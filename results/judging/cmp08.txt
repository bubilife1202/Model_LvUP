=== ANSWER A ===
Write-ahead logging (WAL) is how a database makes you a promise it can keep: "once I say your transaction committed, that change survives a power loss, even if the machine dies one microsecond later." To see why it works, you first have to internalize one uncomfortable fact about ordinary file I/O.

**The lie of `write()`.** When your code calls `write(fd, buf, 8192)`, the bytes do not go to the disk. They land in the operating system's *page cache*: volatile DRAM. The kernel returns success immediately and flushes to the physical device whenever it feels like it, possibly seconds later — and the device itself may then hold the bytes in its own volatile write cache. A `write()` that "succeeded" can evaporate on power loss. The only primitive that forces bytes onto stable storage is `fsync(fd)` (or opening with `O_DIRECT` plus write barriers / FUA), which blocks until the device confirms durability. So `fsync` — not `write` — is the durability primitive. Every claim below rests on this.

**A few terms.** A **page** is the fixed-size block the DB reads and writes as a unit, typically 8 KB (PostgreSQL) or 16 KB (InnoDB); each row lives at some byte offset inside a page. The **WAL** is a separate, append-only file of *log records*, each stamped with a monotonically increasing **LSN** (Log Sequence Number, effectively a byte position in the log). A **checkpoint** is a periodic event where the DB flushes dirty data pages and records "everything up to LSN X is safely in the data files," so recovery can start there instead of from the beginning of time.

**The running example.** You run `UPDATE accounts SET balance = 200 WHERE id = 7`. Row id=7 lives on data page 5, at byte offset 132 within that page (page 5 itself starts at byte offset 40960 in the data file); balance is currently 100. The exact sequence:

1. The DB modifies page 5 *in memory* (the buffer pool): offset 132 now reads 200. The on-disk copy of page 5 still says 100.
2. It appends a WAL record at **LSN 1000**: "page 5, offset 132, old=100, new=200" (plus a transaction id).
3. On `COMMIT`, it appends a commit record at **LSN 1080** and calls `fsync` on the WAL file, which blocks until LSN 1080 is physically durable.
4. **Only after that `fsync` returns** does the DB tell your client "committed."
5. Page 5 itself is still dirty in memory. It is written to its home location on disk *later* — at the next checkpoint, or when the buffer pool needs the slot. Lazily.

**The ordering invariant — the heart of WAL.** The rule is *log before data*: the WAL record describing a change must be `fsync`'d to durable storage *before* the modified data page is allowed to be written to its home location on disk. Step 3 (log durable) strictly precedes step 5 (page written). Why this exact order? The log is the source of truth for redo; if a data page reached disk but its log record did not, a crash would leave a change we can neither explain nor undo. Forcing the log down first guarantees that any change visible in the data file is already described, durably, in the log.

**The commit point.** A transaction is durable the instant its *commit* record is `fsync`'d to the WAL (step 3) — *not* when page 5 is written. This is the key inversion for newcomers: the data page may reach disk much later, or after a crash never — it gets *reconstructed*.

**Recovery (redo).** Say power drops right after step 4 but before step 5. On restart, page 5 on disk still says 100, but you were promised 200. The DB scans the WAL forward from the last checkpoint, finds LSN 1000 and the LSN 1080 commit, sees the change belongs to a committed transaction, and *redoes* it: it re-applies "page 5 offset 132 = 200" to the data page. The WAL is the source of truth; data pages are a cache that recovery rebuilds. Redo replays committed records forward; for any transaction that did *not* get a durable commit record, its changes are rolled back (undo). The direction matters: committed → redo, uncommitted → undo.

**What you lose without this.** Drop WAL and just write data pages in place. The crash now catches you mid-modification with no log to consult. Two distinct disasters. (a) **Acknowledged work vanishes**: you told the client "committed," but page 5 hadn't been flushed yet, and there is no record to redo it from, so the balance=200 is silently lost. (b) **Active corruption**: a multi-page transaction (say it also touched page 9) crashes after page 5 hit disk but before page 9 did. The data files now hold *half* a transaction — debit applied, credit not — internally inconsistent, and with no log you can neither redo it to completion nor undo it. Vague "data loss" misses the point: the specific mechanism is *partial, unordered writes with no record to reconcile against.*

**Group commit.** `fsync` is expensive — a synchronous round-trip to the device (often hundreds of microseconds to milliseconds), and the cost is largely *fixed* per call regardless of payload. One `fsync` per transaction caps single-stream throughput at roughly 1/(fsync latency). **Group commit** batches the commit records of many concurrent transactions into the WAL buffer and flushes them with *one* `fsync`: if 50 transactions have queued their commit records when the flush fires, a single `fsync` makes all 50 durable. It does *not* eliminate `fsync` or weaken durability — every transaction's commit record is still on disk before its client is told "committed." It trades a sliver of latency (a transaction waits a moment for the batch to assemble) for a large throughput gain, amortizing the fixed per-`fsync` cost across the batch.

**Torn pages.** A hardware subtlety. The DB writes page 5 as one 8 KB logical write, but the device only guarantees atomicity at the *sector* level — 512 B, or 4 KB on modern drives. An 8 KB page is 16 × 512 B sectors. If power drops mid-write after sectors 0–2 are written but 3–15 are not, page 5 on disk is a **torn page**: the first ~1.5 KB is new, the rest is old. It is not a lost write and not logical corruption — it is a physically half-updated page that no consistent transaction ever produced, whose internal structures (row pointers, header) may now point into garbage. Note `fsync` does *not* make this 8 KB write atomic across sectors; it only guarantees the bytes reach stable storage, not that all 16 sectors land together.

Two mechanisms handle this, with *distinct* roles. **Full-page writes** (PostgreSQL's term; MySQL's "double-write buffer" plays a similar protective role against torn pages) are *prevention/repair*: the first time a page is modified after a checkpoint, the DB writes the *entire 8 KB page image* into the WAL, not just the offset-132 delta. On recovery, when it reaches that record it overwrites the possibly-torn on-disk page wholesale with that known-good full image from the log, then applies any later deltas on top — giving redo a clean base. **Checksums** are *detection only*: a checksum stored in the page header is recomputed and verified on every read; a torn or rotted page fails the check and is flagged rather than silently trusted. Checksums *find* the damage; full-page writes *fix* it. A checksum can never repair a page.

**The subtle real-world failure: lying disks / fsyncgate.** All of the above assumes `fsync` tells the truth. Two famous ways it doesn't. (1) **Lying disks**: consumer drives and some RAID controllers have a volatile write-back cache and *acknowledge `fsync` before the data actually reaches the platter or flash*, to look fast on benchmarks. The DB believes LSN 1080 is durable and tells the client "committed" — but on power loss that cache evaporates and the acknowledged commit is *gone*. Durability was a fiction the whole stack believed. (2) **Fsyncgate (2018)**: on Linux, if an asynchronous writeback error occurred *after* a `write` but *before* `fsync`, several filesystems would report the error on *one* `fsync` call, then clear the page's dirty flag and drop the failed page — so a *subsequent* `fsync` returned **success** despite the data never reaching disk. PostgreSQL had been retrying `fsync` after an error and treating that later success as proof of durability, silently losing data; the project moved to treating a failed `fsync` as fatal (panic and recover from the WAL) rather than retry. In both cases the consequence is the same and severe: data the database *acknowledged as committed* is silently lost or corrupted on a crash — the exact promise WAL exists to keep, broken by a layer beneath it lying about durability.

## Why WAL + fsync ordering gives you crash-durable transactions

**The core problem.** A database keeps its tables in fixed-size pages (8 KB in PostgreSQL) cached in an in-memory buffer pool. Updates modify pages *in RAM*; writing every modified page to disk at every commit would mean slow, random I/O, and worse, a crash halfway through writing a multi-page transaction leaves disk in a state that is neither "before" nor "after." Without extra machinery, two things go wrong: (1) **lost commits** — you ack a commit whose pages were still only in RAM, then power fails; (2) **corruption/inconsistency** — a crash mid-write leaves one page updated and another not (a transfer that debits but never credits), or a single page only partially written, and after reboot you cannot even tell which pages are bad.

**Running example.** Transaction 7001: move 100 from Alice to Bob. Alice's row lives on heap page 412, balance stored as a 4-byte little-endian int at byte offset 0x1C40: `F4 01 00 00` (500). Bob's row is on page 890, offset 0x09A8: `2C 01 00 00` (300).

The engine modifies both pages **in the buffer pool only**: page 412 becomes `90 01 00 00` (400), page 890 becomes `90 01 00 00` (400). For each change it appends a record to the **write-ahead log**, an append-only sequential file, each record tagged with a monotonically increasing byte position, the **LSN**:

- LSN 0/15E0F30: `xid=7001, page=412, off=0x1C40, old=F4010000, new=90010000`
- LSN 0/15E0F78: `xid=7001, page=890, off=0x09A8, old=2C010000, new=90010000`
- LSN 0/15E0FC0: `xid=7001 COMMIT`

Each dirtied page records the LSN of the last record that touched it (its pageLSN).

**The ordering invariant.** Two rules, enforced with `fsync()` (a plain `write()` only reaches the OS page cache; `fsync` forces it to stable storage, including a flush of the drive's volatile write cache on well-behaved stacks):

1. **Log before data (write-ahead rule):** a dirty data page may be written to disk only after all log records up to its pageLSN are durably flushed. Otherwise a crash could leave a modified page on disk with no log record describing it — if the transaction hadn't committed, you'd have no `old` value to undo it with, and no record that it even happened.
2. **Log before ack (force-at-commit):** the client's COMMIT returns only after the log through the commit record (LSN 0/15E0FC0) has been `fsync`'d. The heap pages themselves can stay dirty in RAM for minutes; the background writer/checkpointer flushes them lazily.

Now enumerate the crash windows. Crash *before* the commit-record fsync completes: the client never received an ack, recovery finds no commit record for 7001 (or a torn log tail, detected by per-record CRCs and treated as end-of-log), and the transaction is simply not redone — correct, since nothing was promised. Crash *after* the fsync but before pages 412/890 ever hit disk: recovery reads the WAL forward, sees the commit record, and **redoes** the changes — writes `90 01 00 00` at 412/0x1C40 and 890/0x09A8. Redo is idempotent: a record is applied only if the on-disk page's pageLSN is older than the record's LSN. Durability of an acked commit therefore reduces to durability of a few hundred log bytes, written **sequentially** — which is exactly what disks are fast at.

**Group commit.** The expensive step is the fsync (~ms on spinning disks, tens of µs on NVMe). It is also shareable: the log is one append-only stream, so a single fsync that pushes the log through LSN X durably commits *every* transaction whose commit record sits at or below X. So when 200 connections commit concurrently, one backend acts as leader, flushes once up to the highest requested LSN, and all 200 wake and ack. Per-transaction commit cost drops from one fsync each to 1/200th of one; throughput becomes bounded by log bandwidth, not fsync latency.

**Torn pages.** An 8 KB page write is not atomic — the device commits 512 B/4 KB sectors, so power loss mid-write to page 412 can leave the first 4 KB new and the last 4 KB old: a structurally invalid page. Page **checksums** detect this on read but can't repair it. Worse, plain WAL redo can't either — many WAL records are deltas that assume the page's prior contents were sane. PostgreSQL's fix is **full-page writes**: the first WAL record touching a page after each checkpoint embeds the full 8 KB page image (with that change applied); recovery *replaces* the torn page with this image wholesale, then applies later deltas on top. (InnoDB instead writes pages twice via a doublewrite buffer.) Torn writes to the WAL itself are benign: per-record CRCs make recovery stop at the first bad record, and anything past the last successful fsync was, by rule 2, never acked.

**When the stack lies.** All of this assumes fsync's contract holds — which it sometimes doesn't. Drives with volatile caches have shipped firmware that acks flushes without persisting (and macOS `fsync` doesn't flush the drive cache; you need `F_FULLFSYNC`). The subtlest case is **fsyncgate** (2018): on Linux, when writeback fails (e.g., a transient storage error), the kernel reports EIO to *one* fsync call, then marks the dirty pages clean — a *retry* of fsync returns success without the data ever reaching disk. PostgreSQL had for ~20 years treated fsync failure during checkpoints as retryable: the retry "succeeded," the checkpoint was declared durable, old WAL segments were recycled — and the never-written page changes were silently lost, unrecoverable because the WAL that could have redone them was gone. The fix: treat any fsync failure as fatal (PANIC), crash, and replay WAL from the last known-good checkpoint. The moral generalizes: durability is a chain — application ordering, kernel semantics, drive firmware — and the invariant is only as strong as its weakest, least honest link.
