=== ANSWER A ===
## Why WAL + fsync ordering gives you crash-durable transactions

**The core problem.** A database keeps its tables in fixed-size pages (8 KB in PostgreSQL) cached in an in-memory buffer pool. Updates modify pages *in RAM*; writing every modified page to disk at every commit would mean slow, random I/O, and worse, a crash halfway through writing a multi-page transaction leaves disk in a state that is neither "before" nor "after." Without extra machinery, two things go wrong: (1) **lost commits** — you ack a commit whose pages were still only in RAM, then power fails; (2) **corruption/inconsistency** — a crash mid-write leaves one page updated and another not (a transfer that debits but never credits), or a single page only partially written, and after reboot you cannot even tell which pages are bad.

**Running example.** Transaction 7001: move 100 from Alice to Bob. Alice's row lives on heap page 412, balance stored as a 4-byte little-endian int at byte offset 0x1C40: `F4 01 00 00` (500). Bob's row is on page 890, offset 0x09A8: `2C 01 00 00` (300).

The engine modifies both pages **in the buffer pool only**: page 412 becomes `90 01 00 00` (400), page 890 becomes `90 01 00 00` (400). For each change it appends a record to the **write-ahead log**, an append-only sequential file, each record tagged with a monotonically increasing byte position, the **LSN**:

- LSN 0/15E0F30: `xid=7001, page=412, off=0x1C40, old=F4010000, new=90010000`
- LSN 0/15E0F78: `xid=7001, page=890, off=0x09A8, old=2C010000, new=90010000`
- LSN 0/15E0FC0: `xid=7001 COMMIT`

Each dirtied page records the LSN of the last record that touched it (its pageLSN).

**The ordering invariant.** Two rules, enforced with `fsync()` (a plain `write()` only reaches the OS page cache; `fsync` forces it to stable storage, including a flush of the drive's volatile write cache on well-behaved stacks):

1. **Log before data (write-ahead rule):** a dirty data page may be written to disk only after all log records up to its pageLSN are durably flushed. Otherwise a crash could leave a modified page on disk with no log record describing it — if the transaction hadn't committed, you'd have no `old` value to undo it with, and no record that it even happened.
2. **Log before ack (force-at-commit):** the client's COMMIT returns only after the log through the commit record (LSN 0/15E0FC0) has been `fsync`'d. The heap pages themselves can stay dirty in RAM for minutes; the background writer/checkpointer flushes them lazily.

Now enumerate the crash windows. Crash *before* the commit-record fsync completes: the client never received an ack, recovery finds no commit record for 7001 (or a torn log tail, detected by per-record CRCs and treated as end-of-log), and the transaction is simply not redone — correct, since nothing was promised. Crash *after* the fsync but before pages 412/890 ever hit disk: recovery reads the WAL forward, sees the commit record, and **redoes** the changes — writes `90 01 00 00` at 412/0x1C40 and 890/0x09A8. Redo is idempotent: a record is applied only if the on-disk page's pageLSN is older than the record's LSN. Durability of an acked commit therefore reduces to durability of a few hundred log bytes, written **sequentially** — which is exactly what disks are fast at.

**Group commit.** The expensive step is the fsync (~ms on spinning disks, tens of µs on NVMe). It is also shareable: the log is one append-only stream, so a single fsync that pushes the log through LSN X durably commits *every* transaction whose commit record sits at or below X. So when 200 connections commit concurrently, one backend acts as leader, flushes once up to the highest requested LSN, and all 200 wake and ack. Per-transaction commit cost drops from one fsync each to 1/200th of one; throughput becomes bounded by log bandwidth, not fsync latency.

**Torn pages.** An 8 KB page write is not atomic — the device commits 512 B/4 KB sectors, so power loss mid-write to page 412 can leave the first 4 KB new and the last 4 KB old: a structurally invalid page. Page **checksums** detect this on read but can't repair it. Worse, plain WAL redo can't either — many WAL records are deltas that assume the page's prior contents were sane. PostgreSQL's fix is **full-page writes**: the first WAL record touching a page after each checkpoint embeds the full 8 KB page image (with that change applied); recovery *replaces* the torn page with this image wholesale, then applies later deltas on top. (InnoDB instead writes pages twice via a doublewrite buffer.) Torn writes to the WAL itself are benign: per-record CRCs make recovery stop at the first bad record, and anything past the last successful fsync was, by rule 2, never acked.

**When the stack lies.** All of this assumes fsync's contract holds — which it sometimes doesn't. Drives with volatile caches have shipped firmware that acks flushes without persisting (and macOS `fsync` doesn't flush the drive cache; you need `F_FULLFSYNC`). The subtlest case is **fsyncgate** (2018): on Linux, when writeback fails (e.g., a transient storage error), the kernel reports EIO to *one* fsync call, then marks the dirty pages clean — a *retry* of fsync returns success without the data ever reaching disk. PostgreSQL had for ~20 years treated fsync failure during checkpoints as retryable: the retry "succeeded," the checkpoint was declared durable, old WAL segments were recycled — and the never-written page changes were silently lost, unrecoverable because the WAL that could have redone them was gone. The fix: treat any fsync failure as fatal (PANIC), crash, and replay WAL from the last known-good checkpoint. The moral generalizes: durability is a chain — application ordering, kernel semantics, drive firmware — and the invariant is only as strong as its weakest, least honest link.

=== ANSWER B ===
Write-ahead logging exists to solve one problem: a buffered database modifies pages in RAM, but a crash can strike at any instant, and the disk only persists what was explicitly flushed and acknowledged. Without WAL, durability and atomicity both collapse.

**Running example.** A bank table stores account balances. Row for account #42 lives on heap page 100 (an 8 KB page). We run `UPDATE accounts SET balance = balance - 100 WHERE id = 42`, changing bytes at offset 6000 in page 100 from `0x000003E8` (1000) to `0x00000384` (900). The buffer manager loads page 100 into a RAM buffer, edits those 4 bytes, and marks the buffer *dirty*. Crucially, it does **not** immediately write page 100 to disk — that would mean a random 8 KB write per transaction, destroying throughput.

**What is lost or corrupted without WAL.** If we acknowledge `COMMIT` to the client while page 100 is still only dirty in RAM, and power drops before the buffer is flushed, the disk still holds balance=1000. The committed debit vanishes: a **durability** violation. Worse, suppose the transaction touched two pages (debit page 100, credit page 205) and only page 205 reached disk before the crash — now $100 was created from nothing: an **atomicity** violation leaving the database logically inconsistent. There is no way to detect or repair this after the fact, because the in-RAM intent is simply gone.

**The fix: log the intent first.** Before modifying page 100 on disk, the database appends a small WAL record to a sequential log file describing the change: *"LSN 5000: page 100, offset 6000, old=0x000003E8, new=0x00000384, txn 77."* The log is append-only, so writing it is a cheap sequential write, not a random one. At `COMMIT` we append *"LSN 5008: COMMIT txn 77"* and then **fsync the log**, forcing those bytes out of the OS page cache and the drive's volatile cache onto stable media. Only after fsync returns do we acknowledge the commit to the client.

**The precise ordering invariant (write-ahead rule).** The log record describing a change must reach stable storage *before* the corresponding data page is allowed to reach stable storage. Formally: a dirty data page may not be written to disk until all WAL records up to that page's LSN are durably flushed. (Each page header stores its last-applied LSN; the buffer manager refuses to evict a page whose LSN exceeds the durable log position.) And a transaction is not "committed" until its commit record is fsynced. *Why this exact order?* The log is the ground truth for recovery. If the data page hit disk first and we crashed before logging, recovery would see a changed page with no record explaining it — unable to undo a possibly-uncommitted change. By logging first, every on-disk data change is always backed by a log record, so recovery can deterministically **redo** committed changes (reapply log records to pages) and **undo** uncommitted ones. After our fsync, even if page 100 never flushed before the crash, recovery replays LSN 5000 onto the on-disk page 100, restoring balance=900. The data pages themselves can be flushed lazily, minutes later, in efficient batches.

**Group commit amortizes fsync.** An fsync is expensive — it waits for a physical platter rotation or a flash program/erase, on the order of milliseconds. If 500 concurrent transactions each fsynced independently, you would be capped at a few hundred commits/sec. Instead the database batches them: transactions 77, 78, 79... append their commit records to the log buffer, then the first one to reach the fsync point holds a brief window while others pile their records onto the same contiguous log tail. A *single* fsync then flushes all of their commit records at once, and every transaction in that batch is acknowledged together. One disk flush durably commits hundreds of transactions, trading a sub-millisecond latency increase for an order-of-magnitude throughput gain.

**Torn pages and full-page writes.** An 8 KB database page is larger than the disk's atomic write unit (a 512 B or 4 KB sector). If power fails mid-write, the drive may persist the first 4 KB of page 100 and leave the last 4 KB as the old contents — a **torn page**, internally inconsistent (e.g., a header pointing past where the row data actually is). Replaying a normal incremental WAL record onto a torn page is unsafe, because the record assumes the page's prior bytes were intact. The standard defense is **full-page writes**: the *first* time a page is modified after a checkpoint, the entire 8 KB image of the page is copied into the WAL. During recovery, that whole-page image is written over the (possibly torn) on-disk page, replacing it wholesale, after which incremental records replay safely. Page-level **checksums** are the detection half: a checksum stored in the page header is verified on read, so a torn or bit-rotted page is caught and flagged rather than silently returning garbage.

**A subtle real-world failure: lying disks / fsyncgate.** WAL's entire guarantee rests on one assumption: when `fsync()` returns success, the data is truly on stable media. Some consumer drives lie — they acknowledge the flush while data still sits in a volatile cache to win benchmarks, so a power cut loses "committed" data despite correct database code. A related, more insidious problem is **fsyncgate (2018)**: on Linux, if a writeback error occurred *after* dirty data left the application but *before* fsync, the kernel could report the error to fsync **once** and then drop the dirty pages and mark them clean. A *retry* of fsync would then return success — even though the data was never written. PostgreSQL assumed a failed fsync could be retried; instead, the second fsync's bogus success let the system believe the WAL was durable when it was not, risking silent data loss. The fix was to treat any fsync failure as unrecoverable and force a crash-recovery cycle (re-deriving state from the known-durable log) rather than trusting a retry. The consequence in both cases is the same: the durability contract is silently broken at the layer beneath the database, and committed transactions can disappear with no error ever surfacing to the application.
