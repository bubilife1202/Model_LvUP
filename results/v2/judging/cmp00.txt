## 1. Problem Statement and Assumptions

We must ingest 200,000 events/second sustained and 300,000 events/second for bursts up to 10 minutes, across three active-active regions, with per-tenant ordering, exactly-once durable storage, and resilience to full regional loss and network partitions.

**Assumptions:** Load distributes equally: ~67K events/s sustained per region, ~100K events/s peak. Producers retry with stable, globally unique event IDs. Cross-region replication latency is under 100 ms normally; partitions may exceed 60 seconds. "Accepted" means durably written to at least two regions before ACK. RPO is zero for accepted events; RTO for full three-region operation is 15 minutes.

---

## 2. Architecture and Rejected Alternatives

**Chosen: Partitioned Kafka per Region with Idempotency Store**

Each region runs a Kafka cluster (replication factor 3) partitioned by `tenant_id` hash, preserving per-tenant ordering without imposing global ordering. A stateless ingestion tier deduplicates against a regional Redis Cluster and writes novel events to Kafka with `enable.idempotence=true` and `acks=all`. Cross-region replication uses Kafka MirrorMaker 2 in active-active mode. Global ordering is explicitly not required.

Each event_id is pinned to a canonical home region via `hash(tenant_id) mod 3`. Non-home regions proxy to the home region. If the home is unreachable for more than 30 seconds, ownership transfers to the next ring node, with a fencing token increment in etcd (quorum across surviving regions) to invalidate stale proxies.

**Rejected Alternative 1: Single-Region Primary with Async Replication.** All writes route through one region. Events ACK'd but not yet replicated are lost during primary failure, violating exactly-once semantics and RPO-zero. Rejected.

**Rejected Alternative 2: Global Shared Database (e.g., CockroachDB as the log).** Global consensus on every write incurs 60–150 ms multi-region round-trip latency, making 200K events/s globally infeasible at acceptable p99. Write amplification from distributed transactions at this throughput exceeds reasonable cost. Rejected.

---

## 3. Capacity Plan

**Sustained ingress per region (67K events/s, 1 KiB avg):**
67,000 × 1,024 B = 68,608,000 B/s ≈ 65.5 MiB/s
65.5 MiB/s × 8 × (1,048,576 / 1,000,000) ≈ 549 Mbps

**Peak ingress per region (100K events/s, 1 KiB avg):**
100,000 × 1,024 B = 102,400,000 B/s ≈ 97.7 MiB/s ≈ 819 Mbps

**Worst-case p95 peak (100K events/s, 4 KiB):**
100,000 × 4,096 B = 409,600,000 B/s ≈ 390.6 MiB/s ≈ 3.28 Gbps. Provision 5 Gbps ingress NICs per region.

**Durable storage per region (7-day retention, average event size):**
65.5 MiB/s × 86,400 s/day ≈ 5,659,200 MiB/day ÷ 1,024 ≈ 5,526 GiB/day ≈ 5.4 TiB/day
× 7 days = 37.8 TiB raw; × replication factor 3 = 113.4 TiB raw per region.
With 1.5× headroom: provision ~170 TiB usable NVMe per region.

**Cross-region replication bandwidth (sustained):**
Each region replicates to two others: 65.5 MiB/s × 2 = 131 MiB/s ≈ 1.10 Gbps outbound.
At peak: 97.7 MiB/s × 2 = 195.4 MiB/s ≈ 1.64 Gbps outbound. Provision 2 Gbps inter-region circuits with burst headroom to 3 Gbps.

**Replay buffer:** 10-minute peak window at average size: 100,000 × 1,024 B × 600 s = 61,440,000,000 B ≈ 57.2 GiB — covered by 7-day Kafka retention. Reserve 75 GiB on-cluster for replay headroom.

## 4. Backpressure Policy

**Low (<50% capacity, <34K events/s):** Accept all events. No throttling. Redis dedup completes under 1 ms.

**Medium (50–80%, 34K–54K events/s):** Accept all. Ingestion tier autoscales. Kafka `linger.ms` raised to 5 ms to improve batching. Alert at p99 write latency >50 ms.

**High (80–100%, 54K–67K events/s):** Per-tenant token-bucket rate limiting activates. Events >16 KiB rejected with HTTP 429 and `Retry-After`. LZ4 compression enabled on producers. All rejections are explicit 4xx; no silent drops.

**Saturation (>100%, >67K events/s sustained or >100K events/s peak):** Gateway returns HTTP 503 with `Retry-After`. In-flight Kafka writes take priority over new connections. No silent drops; producers retry with the same event_id.

**During regional outage:** Each surviving region absorbs ~50% of the lost region's ~67K events/s, reaching ~100K events/s — the designed peak. Both survivors enter High policy immediately on heartbeat timeout (30 s). Load above 100K events/s triggers Saturation policy; DNS failover (30-second TTL) redirects producers, who may receive 503s until autoscaling adds capacity (target: 5 minutes). Backpressure thresholds tighten by 20% to reserve headroom for replication catch-up.

---

## 5. Replay and Deduplication Strategy

**Event ID assignment:** Producers generate a stable `event_id` (UUID v4 or `tenant_id:producer_id:sequence`) before first transmission and reuse it unchanged on every retry.

**Dedup store and crash safety:** The ingestion worker uses a two-phase protocol. Phase 1: execute Redis SET NX on `SHA256(tenant_id + event_id)` with a staging marker (not a Kafka offset) and a 48-hour TTL. If NX returns 0 (key present with any value), the event is acknowledged HTTP 200 with no further action. If NX returns 1 (key absent), proceed to Phase 2: write to Kafka with `enable.idempotence=true` and `acks=all`. On confirmed Kafka write, update the Redis key from the staging marker to the committed Kafka offset.

**Worker crash handling:** If a worker crashes after SET NX (Phase 1) but before the Kafka write commits (Phase 2), Redis holds the key with the staging marker. A background reconciliation process (runs every 60 s) scans keys bearing the staging marker. For each, it attempts the Kafka write idempotently. If the write succeeds, the key is promoted to the committed offset. If the event cannot be written, the key remains as staging until retried. Producers retrying in the meantime receive HTTP 200 with no duplicate write. This closes the crash-window gap: the staging marker prevents double-writes while the reconciler ensures the event eventually lands in Kafka.

**Split-brain dedup:** The home-region ownership model confines authoritative dedup to one region per event. Fencing token increment in etcd invalidates stale proxies before ownership transfers.

---

## 6. Failover and Recovery

**Single-region loss:** DNS health checks reroute producers within 60 seconds (30 s detection + 30 s TTL). Surviving regions apply High/Saturation backpressure. etcd quorum is maintained by two surviving nodes. On recovery, the returning region replays from etcd-checkpointed consumer offsets; MirrorMaker 2 reconciles diverged segments using event_ids as dedup keys.

**Process/worker crashes:** Workers are stateless; Redis and Kafka hold all durable state. Kafka consumer group rebalance completes within 10 seconds. The restarting worker fetches its committed offset from Kafka and resumes. The reconciler handles any staging-marker keys left by the crashed worker, as described in Section 5.

**Producer retries:** Producers retry any non-2xx response with the same event_id. Phase 1 SET NX makes retries universally safe: if the key is present (staging or committed), the request is acknowledged 200 and discarded. If absent, the two-phase write proceeds. Duplicate delivery is impossible regardless of retry count.

---

## 7. Top Three Operational Risks

**Risk 1: Redis dedup store loss.** If a regional Redis Cluster fails, the dedup window is lost, enabling duplicates. Mitigation: 3-way Redis replication with AOF persistence (fsync every second) and automated snapshots to object storage every 15 minutes. If Redis is fully unavailable, ingestion falls back to Kafka transaction log dedup, trading throughput for correctness.

**Risk 2: MirrorMaker lag enabling split-brain dedup.** Replication lag during partial degradation can allow a retry on a different region to bypass dedup. Mitigation: the home-region ownership model confines authoritative dedup to one region per event. MirrorMaker consumer lag is alarmed at a 30-second equivalent backlog (~2 GiB at sustained rate); if exceeded, non-priority tenants are shed to protect replication throughput.

**Risk 3: Kafka partition hot-spotting by high-volume tenants.** A single large tenant saturating one partition stalls per-tenant ordering queues. Mitigation: per-tenant rate cap at the ingestion gateway (default 5,000 events/s, configurable per contract tier); violators receive HTTP 429. A virtual-node consistent-hashing layer allows a tenant to spread across up to 8 sub-partitions, preserving intra-tenant ordering within each shard while distributing broker write load.

=== ANSWER B ===
# Design Memo: Global Event-Ingestion Pipeline

## 1. Problem statement and assumptions

Build a three-region, active-active pipeline ingesting 200k events/s sustained (300k/s peak for ≤10 min), 1 KiB mean / 4 KiB p95, keyed by `tenant_id`, with per-tenant ordering and exactly-once durable storage plus exactly-once downstream effect per event ID, surviving duplicate deliveries, crashes, retries, partitions, and full single-region loss.

Assumptions: (a) producers attach a globally unique, immutable `event_id` (ULID) and retry for at most 7 days; (b) no single tenant exceeds 5,000 ev/s (this is the per-partition ordering ceiling and becomes a contractual limit); (c) the "downstream effect" is a write to an output topic/store, not an unfenceable external side effect; (d) acceptance is meaningful only as "durably quorum-written" — we never ack-then-drop; (e) load splits roughly evenly across regions via geo-routing.

## 2. Architecture (and rejections)

**Chosen:** Per-region partitioned commit log (Kafka-class, RF=3 in-region, acks=quorum), fronted by stateless ingest gateways. Events partition by `hash(tenant_id)` → 512 partitions/region, preserving per-tenant order. Each tenant has a **home region** recorded as a lease (with monotonically increasing epoch) in a global consensus metadata store replicated across all three regions (quorum = 2 of 3, so it survives one region loss). Processing uses log transactions (read–process–write with offsets committed atomically). The authoritative deduplication/effect ledger is a replicated KV store with conditional insert on `event_id`. Each region asynchronously mirrors its ingested log to one peer (ring topology) for replay after region loss.

**Rejected A — single global strongly-consistent log** (stretch cluster or Spanner-backed queue): every write pays cross-region quorum latency (~60–120 ms RTT), throughput collapses under partition, and a partition can stall all ingestion rather than degrading per-tenant. Cost and blast radius are both worse.

**Rejected B — at-least-once pipeline, consumers dedup:** pushes correctness onto every downstream team; one forgetful consumer violates the exactly-once contract. Dedup must be a platform invariant, enforced once.

**Rejected C — active-passive DR:** violates the active-active requirement, wastes ~33% of fleet capacity, and untested passive paths fail when exercised.

## 3. Capacity plan

**Ingress.** Sustained: 200,000 × 1 KiB = 195.3 MiB/s ≈ 1.6 Gbps globally; 66.7k ev/s ≈ 65 MiB/s per region. Peak: 300,000 × 1 KiB = 293 MiB/s ≈ 2.5 Gbps. Size load balancers/NICs to the p95-heavy bound: 300,000 × 4 KiB = 1,172 MiB/s ≈ 9.8 Gbps globally (~3.3 Gbps/region; ~10 Gbps/region during single-region survival worst case) — provision 2×25 GbE per gateway tier per region.

**Durable storage.** Daily raw: 200k × 86,400 = 17.28 B events × 1 KiB = 16.1 TiB/day. In-region RF=3 → 48.3 TiB/day; ring mirror duplicates each event in one peer at RF=3 → 96.6 TiB/day fleet-wide. At 7-day log retention: 676 TiB; +30% for indexes/compaction slack ≈ 880 TiB → provision 300 TiB NVMe per region.

**Dedup ledger.** 7-day window = 121 B keys × ~40 B (16 B id + epoch + offset metadata) ≈ 4.4 TiB logical; ×RF3 ≈ 13.2 TiB — small.

**Replication network.** Per-region mirror egress: 65 MiB/s sustained (0.55 Gbps), 98 MiB/s at peak (0.82 Gbps). Provision 5 Gbps per inter-region link (≈6× headroom). After a 1-hour partition, backlog = 65 MiB/s × 3,600 ≈ 229 GiB; catch-up at (596 − 65) ≈ 531 MiB/s drains in ≈ 7.4 minutes.

**Processing and replay.** Each region's consumer tier is sized for 200k ev/s. Losing one region mid-outage for 1 hour strands 66.7k × 3,600 = 240 M events; the two survivors replay at 50k ev/s each alongside 100k ev/s live → 240 M / 100k = 40 minutes to drain.

**Headroom.** Normal utilization: 66.7k / 200k = 33% per region. Worst case (one region down, 10-min peak): 150k/s live per survivor = 75% utilization, with replay paused. Partition load at that worst case: 150k / 512 ≈ 293 ev/s/partition — far under the ~5,000 ev/s per-partition ceiling.

## 4. Backpressure policy

Defined against per-region provisioned capacity C = 200k ev/s, enforced at gateways via per-tenant token buckets. Invariant at every tier: HTTP 202 is returned only after quorum-durable log append; if durable append cannot complete in 250 ms, reject — never buffer-and-ack.

- **Low (<40% C):** accept everything; linger/batching 5 ms; replay and mirror catch-up unthrottled.
- **Medium (40–70% C):** batching linger rises to 25 ms; per-tenant buckets enforce 1.5× contracted rate; replay capped at 25% of capacity. No rejects.
- **High (70–90% C):** over-quota tenants get 429 + Retry-After (jittered exponential backoff expected); tier-2 (non-critical) events diverted to an object-store spill queue for deferred ingest; replay capped at 10%.
- **Saturation (>90% C, or append p99 > 250 ms, or ISR shrink):** global admission capped at 90% C with max-min fair share across tenants; excess rejected 429; replay and mirroring catch-up paused; tier-2 fully spilled.

**During regional outage:** survivors' absolute load doubles, so triggers fire at the same C thresholds but the policy hardens one notch: tenant buckets drop to 1.0× contracted rate immediately, tier-2 spills at the *medium* tier, and replay budget is 25% maximum, 0% whenever live load exceeds 70% C. Recovery of the failed region reverses these steps only after replay backlog < 5 minutes.

## 5. Replay and deduplication (exactly-once mechanics)

Three layers, only the last authoritative:

1. **Producer/gateway:** producers reuse the same `event_id` on retry; gateways keep a 10-minute LRU/bloom cache to cheaply drop hot duplicates. Best-effort only.
2. **Log transactions:** consumers use transactional read–process–write: output records and input offsets commit atomically; `transactional.id` fencing means a crashed worker's zombie transaction aborts on rebalance. This gives exactly-once *within* a region across crashes.
3. **Effect ledger (authoritative, cross-region):** before the downstream effect is emitted, the worker performs a conditional insert of `(event_id → tenant epoch, offset)` into the ledger in the same transaction as the effect record. Insert succeeds → effect emitted once; key exists → duplicate dropped. The ledger also validates the tenant's **lease epoch**: a commit carrying a stale epoch is rejected, fencing any region that lost ownership during a partition.

Checkpoints are simply committed offsets; replay always restarts from the last replicated checkpoint *minus* an overlap window, because the ledger makes reprocessing idempotent. Ledger retention (7 days) matches the maximum producer retry horizon, so a retry can never outlive its dedup record.

## 6. Failover and recovery

**Producer retries:** identical `event_id`, any region, any time within 7 days → ledger conditional insert drops the duplicate. Timeout-then-retry to a different region is safe for the same reason.

**Process crash:** consumer group rebalances; transactional fencing aborts in-flight work; the new worker resumes from the last committed offset. No loss, no duplicate effect.

**Region loss:** geo-DNS drains traffic to survivors (<60 s). The control plane (quorum intact at 2/3) transfers the dead region's tenant leases with incremented epochs. Survivors replay the mirrored log from the last replicated checkpoint; overlap duplicates are absorbed by the ledger; drain time ≈ 40 minutes per Section 3.

**Partition (region alive but isolated):** the minority region cannot renew leases, so it stops accepting writes for affected tenants and returns 503; producers fail over via geo-routing. The majority side takes leases with higher epochs; any in-flight commits from the isolated region are rejected by epoch check. We explicitly choose consistency over availability per tenant during partitions; mirror catch-up (≈7 min for a 1-hour partition) restores symmetry after heal.

## 7. Top risks and mitigations

1. **Hot tenant exceeds the per-partition ordering ceiling (~5,000 ev/s).** Mitigate: contractual cap, per-tenant skew dashboards alerting at 60%, and an opt-in sub-key sharding mode for tenants who relax ordering.
2. **Dedup ledger on the hot path becomes a latency or availability bottleneck.** Mitigate: batched conditional inserts inside the existing transaction, regional ledger shards with epoch-fenced async merge, and fail-closed behavior (503) on ledger unavailability — never fail-open.
3. **Replay storms after heal/failover compound live load.** Mitigate: hard replay budgets from Section 4, strict priority of live over replay, and monthly game days that exercise region kill plus peak load to validate the 40-minute drain figure.
