=== ANSWER A ===
**Approach selection.** Three candidates: (1) App-level dual-write: no WAL pressure, but the two writes are not atomic — partial failures at 18,000 writes/s silently lose acknowledged data — and the synchronous second write attacks the p99 +25% latency budget. (2) Trigger-based capture (pg_repack-style): transactional and lossless, but row triggers tax every hot-path write and the queue table adds bloat and vacuum pressure. (3) Logical-decoding CDC: a publication plus a logical replication slot (pgoutput, consumed by a Debezium-style applier) streams committed changes in LSN order with zero added write latency; the consumer reshapes each wide row into the normalized tables and remaps keys — which native logical replication's table-to-table model cannot. Cost: the slot pins WAL until confirmed, so retention must be managed. **Chosen: (3)** — the only option handling 2 TB, a table split, and a PK change without touching write-path latency. Native subscription `copy_data=true` is rejected: a single 2 TB initial sync retains WAL and holds back vacuum for hours.

**Phase 1 — Preflight and baseline.** Confirm the source PK exists — it satisfies the replica identity logical decoding requires for UPDATE/DELETE. Capture 7-day baselines: p99 write latency, error rates, autovacuum cadence. Require ≥25% free disk; set `wal_level=logical`, raise `max_wal_senders`/`max_replication_slots`, and set `max_slot_wal_keep_size=300GB` so a stuck slot kills the migration, never the database. Rehearse the pipeline, cutover, and rollback on a restored 2 TB clone, measuring drain time.

**Phase 2 — Target schema and coexistence (expand).** Create the normalized tables empty — no locks touch the source. New tables use the new PK (e.g., UUIDv7); every row also carries `legacy_id` under a UNIQUE index — a bidirectional key map during transition. The two generated columns are declared `GENERATED ALWAYS ... STORED` on the target and computed there on insert — change streams never carry stored generated columns. Coexistence is expand/contract: old code keeps reading/writing the wide table; app vN+1 ships a flag-gated data layer reading/writing either schema; a compatibility view reconstructs the wide shape from the normalized tables (joined on `legacy_id`) for lagging readers after cutover. Lock rules: all source-side DDL runs with `lock_timeout='2s'` plus retry, so a blocked ACCESS EXCLUSIVE attempt self-cancels instead of queueing and stalling writers; foreign keys are added `NOT VALID` then `VALIDATE CONSTRAINT` later (SHARE UPDATE EXCLUSIVE — never blocks writers); all post-backfill indexes use `CREATE INDEX CONCURRENTLY`; no `ALTER ... TYPE` or volatile-DEFAULT change that rewrites the 2 TB heap is ever permitted.

**Phase 3 — Backfill.** Create the publication and slot first to pin the start LSN, then backfill via keyset pagination on the source PK in 10,000-row batches reading live data — deliberately not one weeks-long repeatable-read snapshot, which would block vacuum. Each batch upserts with `INSERT ... ON CONFLICT (legacy_id) DO UPDATE ... WHERE excluded.src_version > target.src_version`; CDC started first, so rows mutated mid-backfill are corrected by replay, deleted rows vanish from later batch reads, and the rare in-flight resurrection is caught by reconciliation. Throttling: pause entirely when slot-retained WAL (`pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)`) exceeds 100 GB, apply lag exceeds 60 s, or p99 write latency exceeds baseline +15% — lag stays bounded because the applier always outranks backfill for capacity. Per-batch verification: row counts plus an `md5(string_agg(...))` checksum of the normalized projection of that key range; failed chunks requeue.

**Phase 4 — CDC apply, idempotency, reconciliation.** The applier consumes in LSN order, applying upserts keyed on `legacy_id`, guarded by a per-row `last_applied_lsn` (apply only if newer) and a row-wise `IS DISTINCT FROM excluded` check to suppress no-op writes; unchanged-TOAST placeholders preserve existing target values. It persists its confirmed-LSN watermark in the same transaction as the data, so crash replays and duplicates are no-ops — acknowledged writes are never lost or double-applied. Reconciliation re-checksums random plus recently-modified key ranges hourly, alerting and auto-repairing on mismatch; cutover is blocked until two consecutive clean full passes.

**Phase 5 — Validation.** Steady-state apply lag <5 s for 48 h; row counts equal; aggregate invariants (sums, `max(updated_at)`) match; dark reads — new code reads both schemas, compares, serves old — with zero mismatches for 24 h. Reads never move until this gate passes, protecting 99.99% read availability.

**Phase 6 — Cutover (budget 30 s; target 15 s) and rollback.** Checklist: (1) preconditions: lag <1 s for 10 min, reconciliation clean, off-peak; (2) t=0: PgBouncer `PAUSE` on the write pool only — writes queue rather than error (protecting 99.95% write availability; a ≤20 s pause fits the ~21-minute monthly budget) while reads flow untouched; (3) capture the fence LSN via `pg_current_wal_lsn()`; (4) wait until the applier watermark reaches the fence LSN — abort and `RESUME` if not drained by t+10 s; (5) checksum the last-hour slice (<5 s); (6) flip the flag — reads and writes route to the new schema — and stop the forward consumer; (7) start reverse CDC (pre-created slot on the new tables, inverse transform new→old) from the cutover LSN — only one direction is ever active, so no echo loop; (8) canary write/read; (9) `RESUME`. **Rollback** any time ≤72 h: fence (≤10 s), drain reverse CDC to zero, flip the flag back, resume — post-cutover writes were already replicated into the old table, never restored from backup.

**Phase 7 — Cleanup (contract).** After 7 clean days: stop reverse CDC and drop both slots immediately (orphaned slots retain WAL forever); drop the compatibility view once query logs show zero hits for 72 h; `VALIDATE` remaining constraints; archive, then drop the old table; remove dual-path code and legacy-key generation.

**Abort criteria.** Pause backfill: retained WAL >100 GB, apply lag >60 s, or p99 >baseline +15% for 5 min. Halt the migration: disk free <15%; p99 write latency >baseline +20% for 5 min (hard floor inside the +25% SLO); write error rate >0.02% or read error rate >0.005% over any 5-min window (guarding 99.95%/99.99%). Abort cutover: drain incomplete at 10 s; any checksum mismatch. Abandon and roll back: reconciliation finds divergence twice after repair, or retained WAL >250 GB.

**Top three risks.** (1) Slot-induced WAL bloat exhausting primary disk: alerts at slot-retained WAL >50 GB, `confirmed_flush_lsn` unchanged 5 minutes, and disk-free slope projecting exhaustion within 24 h. (2) Backfill-driven latency and vacuum starvation on the hot table: alert at p99 >baseline +10% via pg_stat_statements, lock waits in pg_locks, and `n_dead_tup` growth >2× the weekly norm. (3) Silent divergence from transform edge cases (NULL semantics, encodings, type coercion): first-mismatch alert from hourly reconciliation plus a zero-tolerance alarm on the applier's dead-letter queue depth.

# Zero-Downtime Migration Plan: 2 TB Hot-Path Table → Normalized Schema

## Approach Selection

**Dual-write (application writes both schemas):** Pro: no replication infrastructure, transformation logic lives in code. Con: it puts a second synchronous write on the hot path, which at 18k writes/sec will almost certainly breach the +25% p99 latency SLO; partial-failure handling (old succeeds, new fails) creates divergence that requires constant reconciliation; and any app crash window can silently drop changes, threatening the "no lost acknowledged writes" SLO.

**Logical replication / CDC (consume WAL, transform, apply):** Pro: zero added latency on the write path (capture is asynchronous, after commit); acknowledged writes are durable in WAL before capture, so nothing acknowledged can be lost; ordering and exactly-the-committed-data semantics come for free. Con: WAL/slot retention risk, and native `CREATE SUBSCRIPTION` cannot reshape a wide row into normalized tables.

**Decision:** CDC via a native logical replication slot (`pgoutput`/`wal2json`) consumed by a transform-and-apply service writing the normalized tables. It satisfies the latency and durability SLOs by construction; dual-write fails both. The schema reshaping that rules out plain `CREATE SUBSCRIPTION` is handled in the consumer.

## Phase 0 — Preflight (1–2 weeks)

- Confirm `wal_level=logical`, `max_replication_slots`, and ≥25% free disk headroom for WAL retention; verify backups and PITR.
- Capture baselines: p50/p99 write latency, QPS, autovacuum cadence, checkpoint behavior, bloat.
- Set `lock_timeout = 2s` and `statement_timeout` for all migration DDL; every DDL retries in a loop rather than queuing behind it (a waiting `ACCESS EXCLUSIVE` blocks *all* traffic behind it — this is how migrations cause outages).
- Set `REPLICA IDENTITY` on the source. If the existing PK suffices, no change; if `FULL` is required, accept the WAL volume increase and load-test it on a clone. The `ALTER` takes a brief exclusive lock — run with the 2s lock_timeout/retry loop.
- Rehearse the entire runbook, including cutover and rollback, on a PITR clone with replayed production traffic.

## Phase 1 — Expand: New Schema and Compatibility Layer

- Create the normalized tables with generated columns defined locally (they're computed on insert, so CDC never replicates them). New PKs (e.g., UUIDv7/sequence) are assigned by the apply service; a `pk_map(old_pk → new_pk)` table makes the mapping deterministic and idempotent.
- Create only the unique indexes needed for idempotent upserts now; defer all secondary indexes until after backfill (then build with `CREATE INDEX CONCURRENTLY`), roughly halving backfill write amplification.
- **Schema compatibility:** expand/contract. Old app versions keep reading/writing the wide table untouched. New app versions go through a repository layer (or updatable view) keyed by the *old* PK, which remains a unique, indexed column in the new schema. No old-version code ever needs to know the new schema exists; contract (remove old paths) happens only in cleanup.

## Phase 2 — Snapshot + Backfill

- Create the logical slot with `CREATE_REPLICATION_SLOT ... EXPORT_SNAPSHOT`; backfill reads from that exported snapshot so the slot's LSN is an exact consistency boundary — no gap, no overlap.
- Backfill via keyset pagination on the old PK (`WHERE pk > $last ORDER BY pk LIMIT 10000`), never `OFFSET`. Each batch is one short transaction; progress checkpointed to a control table so it's resumable.
- **Throttling:** adaptive controller. Pause when physical replica lag > 10s, p99 write latency > baseline +15%, or active autovacuum on the source; resume below thresholds. Target ≤ 30 MB/s; at that rate 2 TB completes in ~3–5 days — acceptable.
- Run backfill off a physical replica if available to spare primary read capacity.

## Phase 3 — CDC Tailing + Reconciliation

- The apply service consumes the slot from the snapshot LSN, transforms each row change into normalized writes inside one transaction, using `INSERT ... ON CONFLICT (old_pk) DO UPDATE` — fully idempotent, so crash/replay is safe. It acknowledges (advances `confirmed_flush_lsn`) only after commit on the target: at-least-once delivery + idempotent apply = no loss.
- Lag stays bounded because steady-state change volume (18k wps) is far below apply throughput once backfill ends; alert at >30s lag, page at >120s.
- **Verification:** (a) per-range counts; (b) chunked checksums — `SELECT count(*), sum(hashtext(concat_ws('|', cols...))) ... WHERE pk BETWEEN x AND y` against an equivalent join on the new schema; (c) continuous random sampling of ~1,000 rows/min, full-column compare. Require 48h of zero mismatches before cutover.

## Phase 4 — Cutover (target < 30s, budget 30s)

Checklist:
1. CDC lag < 1s for 15 min; checksums green; secondary indexes built and `VALID`; `ANALYZE` run on new tables.
2. Start **reverse CDC** (new → old, skipping echoes via origin filtering) idle and ready, for rollback.
3. Fence writes: `PAUSE` via PgBouncer or app write-flag (reads continue uninterrupted — protects the 99.99% read SLO).
4. Wait for CDC to drain to the fence LSN (expected < 5s). Hard abort at T+20s.
5. Flip the application write/read flag to the new schema; smoke-test one synthetic write.
6. `RESUME`. Total fence: 5–15s typical.

**Rollback:** flip the flag back to the old table; reverse CDC has been keeping it current, so rollback is another <30s fence at any point during the 7-day soak. Keep reverse replication running that whole week.

## Abort Criteria (any one → pause/abort)

- p99 write latency > baseline +20% for 5 consecutive minutes (buffer under the 25% SLO).
- Write error rate > 0.02% over 5 min (99.95% budget guard).
- CDC lag > 300s or retained WAL > 200 GB.
- Source disk > 80% full.
- Reconciliation mismatch rate > 0.001% of sampled rows, or any mismatch unexplained within 1 hour.
- Cutover drain not complete at T+20s → unfence on old schema immediately.

## Top Three Operational Risks

1. **Slot-induced WAL retention filling disk** (consumer stalls, WAL accumulates, primary goes read-only — an availability outage). Detect: alert on `pg_replication_slots.restart_lsn` age and retained-WAL bytes at 50 GB, page at 100 GB; pre-agreed last resort is dropping the slot and restarting backfill from a new snapshot.
2. **Backfill pressure degrading the hot path** (vacuum debt, checkpoint storms, replica lag). Detect: the adaptive throttle's own metrics, dead-tuple counts, and a canary write probe measuring p99 every 10s against baseline.
3. **PK-mapping or transform defects causing silent divergence** (wrong joins after normalization). Detect: continuous sampling reconciliation from day one—not just pre-cutover—plus dark reads: serve from old, shadow-query new, diff results at 1% of read traffic and alert on >0.01% mismatch.

## Phase 5 — Cleanup (after 7-day soak)

Stop reverse CDC, drop both slots, remove old-schema code paths and the compatibility layer, archive then drop the wide table (`DROP` takes only a momentary lock), reclaim space, and update runbooks with rehearsal-vs-actual timings.
